## 1. Executive summary

The three systems are **complementary, not overlapping, at the domain level** — and almost entirely **disconnected at the infrastructure level**. That is good news: there is no competing compute platform to unwind in either domain repo, but also no integration to build on. Every remote-compute path is either plan-only or untested.

Headline findings:

1. **Polygrow's Intelligence Compute Platform (Modal) is plan-only.** Specification B (`docs/plans/phase 2/Polygrow Intelligence Compute Platform.md`, 1,761 lines, untracked, saved 2026-11-19) defines the `intelligence/` domain, `ComputeJob`, workload profiles, and a `ComputeProvider` adapter — none of it exists in code. There is **zero Modal code** in Polygrow (every `modal` hit is the word "modality"), no model registry, no training/fine-tuning code, no Developer API, no credit ledger.
2. **Rustenwer has zero Modal code and one untested remote provider.** Its only remote compute is DigitalOcean (`api/app/training/providers.py`), code-complete but never live-tested and credential-blocked. The only working execution is local CPU. Its real asset is the framework-free domain core in `shared/` (diagnosis, methods, experiments, memory) plus real torch training adapters.
3. **Syrius has zero remote-compute code of any kind.** One validated RL slice (CartPole-v1 + SB3 PPO on CPU) through a Postgres job queue + local Docker worker. No auth, no tenancy, no GPU provider. Its real assets are independent evaluation, the reproducibility manifest + validated policy package, and the 71-tool registry.
4. **The clean seams already exist.** Rustenwer's `ComputeProvider` Protocol is the exact seam a Modal provider plugs into (though its SSH/subprocess shape needs reshaping). Syrius's tool registry (`GET /capabilities/tools`, `POST /capabilities/tools/{name}/run`) is the natural contract surface. Polygrow's outbound MCP client + Capability Engine is the natural hook-in surface — a Rustenwer/Syrius MCP server would slot in without new plumbing.
5. **Nothing in this change removes or replaces working functionality.** Phases R1–R4 / S1–S4 are not started; they are sequenced in §9 as open work for Roger's decision.

### 2.2 Rustenwer — implemented

Rustenwer is a **local-CPU, in-memory, single-tenant model-engineering workbench** with a strong pure-domain core. Full lifecycle, all verified in code at `main` @ `174b254`:

- **Spec / intake:** `IntelligenceSpec` CRUD (`api/app/specs.py`).
- **Diagnosis (decide before compute):** deterministic 7-stage pipeline (`shared/services/diagnosis.py:run_diagnosis`); 8 `IntelligenceStrategy` values; **DO NOT TRAIN is a first-class outcome**; NEEDS_HUMAN escalation; RAG/agent outcomes are explicitly Polygrow-handoff recommendations only.
- **Discovery:** veto/rank engine + Hugging Face Hub catalog, public API, no key, injectable transport (`shared/services/discovery.py`, `hf_catalog.py`).
- **Baselines:** 4 baseline kinds; `CapabilityEvaluator` runs candidates on versioned samples → measured `QualityVector`s; evaluation-definition versioning + sacredness guards (duplicate train/eval, temporal leakage); data lineage (`shared/services/capability.py`, `evaluation_definitions.py`, `lineage.py`).
- **Method recommendation:** pure engine, ranked methods + explicit vetoes as negative-search data (`shared/services/methods.py`).
- **Dataset preparation:** schema inference, leakage detection, split recommendation — deterministic checks only, on in-memory rows. No ingestion pipeline, no real-dataset loader.
- **Training:** real torch CPU adapters — Classifier (MLP), LoRA, QLoRA (real Unsloth, CUDA-only, honest refusal on CPU), Distillation, Contrastive (`api/app/training/adapters.py`, ~1,330 lines). Phase 2 trains on deterministic synthetic seeded data; real user datasets plug into `prepare()` in Phase 3+.
- **Fine-tuning:** LoRA/QLoRA adapters (no separate fine-tuning service).
- **Optimization / compression:** only QLoRA 4-bit quantization and distillation. No pruning, no ONNX export, no standalone quantizer.
- **Evaluation:** `QualityVector` (lexicographic rank by spec priority), metrics (accuracy, per-class accuracy, ECE, Brier), benchmark registry, threaded evaluation runner, comparison reports.
- **Experiments:** candidate = testable hypothesis (hypothesis + evidence + expected improvement + estimated cost, enforced at the API boundary); lifecycle PROPOSED → … → SUCCEEDED/FAILED/CANCELLED/REJECTED; budget enforcement; §20 stopping policies incl. Pareto smaller-model dominance.
- **Experiment memory:** per-project outcomes, engineering conclusions, negative search (`MemorySkip`, ruled-out method@version never re-proposed); global `strategy_effectiveness` aggregates with customer-data isolation allowlist.
- **Registry / storage / checkpoints:** `Intelligence` is the product entity; immutable `IntelligenceVersion` + sha256 `version_digest` at publish; local immutable artifact store (sha256 re-verified on read); torch checkpoints saved/loaded atomically.
- **Inference / serving:** hosted pipeline (validate → execute architecture components → shape output). Only `RUSTENWER_HOSTED` executes; `EXTERNAL_API` and `LOCAL_GPU` raise `ProviderNotConfigured`.
- **Deployment:** promotion gate (evidence + baseline comparison + policy/security + cost + human approval); lifecycle DRAFT → DEPLOYING → ACTIVE (+ UP/DOWN states); rollout plans (only PRODUCTION executes; staging/shadow/canary honestly not-implemented); rollback keeping previous version; `rw_`-prefixed API keys (hash-only, shown once); OpenAI-compat `/v1/models` + `/v1/chat/completions`; cost accounting (estimated vs actual vs price vs margin).
- **Packaging:** adapter `export()` writes a torch bundle into the artifact store. No container image, no model-card generation, no ONNX/TensorRT packaging.

### 2.3 Syrius — implemented

Syrius v0.1 (Phases 0–7 complete, 2026-11-14) is a **real, narrow, single-environment RL slice**: CartPole-v1 + SB3 PPO on CPU, through a FastAPI + Postgres job queue + local Docker worker. Verified in code at `main` @ `0745711`:

- **Spec (Architect):** free text → structured `RLProblemSpecification` (versioned); rule-based only; AI generation BYOK-optional, never called in slice (12 Architect tools).
- **Environment:** `gym.make(gym_id)`; validation = `gymnasium.check_env` + 1 smoke episode. Built-in registry is only 6 ids (CartPole-v1/v0, MountainCar-v0, Acrobot-v1, LunarLander-v3, Pendulum-v1). **Only CartPole-v1 ever validated end-to-end.** No custom-env registration, no env code upload.
- **Reward / termination:** entirely Gymnasium-native — no Syrius reward shaping. Success is defined independently of training reward: episode counts as success iff length ≥ 500.
- **Simulation / rollouts:** `run_episode(env, policy, seed, deterministic)`; per-step trace only when `record=True`; safety cap 10,000 steps. Random baseline: 20 episodes, `seed+i`.
- **Experiment design:** one `Experiment` = one `TrainingConfig` + one env + one algorithm string. **No sweep, no multi-arm design, no scenario matrix.** Comparison is post-hoc dict comparison of two runs' stored metrics. `Scenario` model exists but has no API route.
- **Training (PPO only):** SB3 `PPO("MlpPolicy", …)`, `model.learn(total_timesteps)`, progress callback every 512 steps → `metrics.csv` + DB `current_step`. **CPU only** (torch 2.15.0+cpu). Default: 20,000 steps, lr 0.0003, n_steps 2048, batch 64, epochs 10, gamma 0.99, gae 0.95, clip 0.2. Algorithm field is a free string, but only PPO is ever instantiated; SAC is a label only.
- **Checkpoints:** exactly one per training run (`final_model.zip`, `step = total_timesteps`). No mid-training checkpoints, no best-checkpoint tracking. Selection = latest by step desc. **No promotion, no staging/prod state, no rollback** (`RollbackPolicy` is `not_implemented`).
- **Evaluation / comparison:** independent — fresh `PPO.load()`, fresh env, N rollouts (seed+i, default seed 100, deterministic). Metrics: mean/median/min/max reward, mean/median length, `success_rate`, `successes`. Baseline comparison and `report.json`/`report.md` generated from stored metrics, not re-run (except `VerifySuccessIndependently`, 5 eps / seed 1000).
- **Policy / export:** `Policy` row points at a checkpoint; export builds `manifest.json` + zips `final_model.zip + manifest.json + README.md`, then **independently validates** the package (extract to tempdir, fresh load, 5 eps seed 1000).
- **Storage:** DB rows are pointers only (`Artifact.storage_uri`, `sha256`, `size_bytes`); bytes in artifact storage; episode traces in storage, never Postgres.
- **Metrics / reproducibility:** seeds in `TrainingConfig`; per-episode `seed+i` offsets; manifest records env/algorithm/full config/hyperparams/seeds/framework versions. **Gaps:** `env_version` hardcoded `1` in `execute_export`; baseline mean non-reproducible run-to-run with the same seed (16.95–23.35 across 6 runs, documented); no run-level git/commit or dataset hash.

**Measured evidence (Phase 7 E2E, 2026-11-14):** baseline mean 21.90; PPO 20k steps in 54.3 s; eval mean 498.70/500, success 0.95 (19/20); export independently validated mean 492.80, success 0.80; package 115,041 bytes, sha256-verified.

## 4. Specialized capabilities worth preserving

### 4.1 Rustenwer — preserve and expose

1. **Diagnosis-first pipeline** (`shared/services/diagnosis.py` + `methods.py`) — deterministic, framework-free, decides DO NOT TRAIN / existing-model / distill / fine-tune _before_ spending compute, with auditable evidence and vetoes as negative-search data. The product's actual moat (smallest sufficient intelligence). Cleanly separable as a pure library. Exposable verbs: `diagnose_spec`, `recommend_methods`.
2. **Experiment engine + experiment memory** (`shared/services/experiments.py` + `memory.py`) — hypothesis-driven candidates with enforced budgets, Pareto stopping policies, and a memory that provably never re-proposes a ruled-out method@version. The learning loop that makes each engagement cheaper than the last; no equivalent in generic orchestration. Exposable verbs: `generate_candidates`, `decide`, `consult_memory`.
3. **Intelligence registry + promotion gate + OpenAI-compat serving** (`api/app/registry/intelligences.py`, `shared/services/promotion.py`, `api/app/intelligence/inference.py`, `api/app/openai_compat.py`) — immutable versioned intelligences with sha256 digests, a deterministic evidence-based promotion gate, and a standard `/v1/chat/completions` surface. This is the "Intelligence is the product, Model is an implementation detail" contract — the natural interface Polygrow would consume. Exposable verbs: `publish_intelligence_version`, `evaluate_promotion`, `serve_intelligence`.

### 4.2 Syrius — preserve and expose

1. **Independent evaluation with success decoupled from training reward** (`rl.py:evaluate_policy`, `executor.py:execute_evaluate`, `tools.py:VerifySuccessIndependently`) — fresh `PPO.load()`, fresh rollouts, success = full 500-step episode, plus random-baseline comparison and report generation. The honest-measurement core; what makes a trained policy trustworthy to a third party. Exposable verbs: `evaluate_policy`, `verify_success`, `compare_baseline`.
2. **Reproducibility manifest + independently-validated policy package** (`rl.py:build_manifest`, `build_delivery_package`, `validate_delivery_package`) — full config/hyperparams/seeds/framework versions in `manifest.json`, zip with model + manifest + README, validation by fresh load + rollouts in a tempdir. The closest thing in the repo to a shippable RL artifact contract. Exposable verbs: `export_policy`, `validate_policy_package`.
3. **The 71-tool department registry as a typed capability surface** (`tools.py:_TOOL_TABLE`, `capabilities.py:EngineeringCapability`, `routers.py:/capabilities/tools…/run`) — 65 real handlers spanning spec → env → experiment → evaluation → deployment, with honest `not_implemented` + human-approval gating for the 6 that cannot run. The natural seam for Polygrow to call ("run `TrainPolicy` / `RunEvaluation` / `ValidatePolicyPackage`") without adopting Syrius's API, queue, or UI wholesale.

### 4.3 Polygrow — preserve as the integration surface

MCP client (outbound) + Capability Engine registry/discovery, Workflow Engine, cost-event recording, artifact metadata/versioning, Skill canary/shadow deploy pattern, LLMRouter + Jev selection policy, promptfoo + agent evals. Extend these for model/RL workloads rather than starting parallel stacks. Do not rebuild a sandbox (E2B/Vercel exist), a second workflow engine (Spec B §15.3 forbids it), or a parallel billing path (extend cost events into the credit ledger).

## 7. Proposed target architecture

```
                     POLYGROW
              Central Intelligence Platform
                         |
              Mind / Orchestration (LangGraph)
                         |
              Intelligence & Compute Platform
              (Spec B: intelligence/ domain)
                         |
              Compute Provider Interface
              (ComputeProvider adapter)
                         |
                       Modal
                         |
               Remote CPU / GPU
                         |
             Durable Artifact Storage
                         |
           -----------------------------
           |                           |
       Rustenwer                    Syrius
   Model Engineering             RL Engineering
           |                           |
   Model Workloads               RL Workloads
   Training                      Simulations
   Fine-tuning                   Rollouts
   Optimization                  Policy Training
   Evaluation                    RL Evaluation
   Inference                     Checkpoints
           |                           |
           -----------------------------
                         |
              Results / Artifacts
                         |
                     POLYGROW
```

Rules that govern the target:

1. **Polygrow owns** central intelligence orchestration, general compute job lifecycle, Modal integration and credentials, remote CPU/GPU execution infrastructure, tenant identity and authorization, shared budgets/credits/usage, general artifact infrastructure, shared model/intelligence resource lifecycle, the general Developer API, the user-facing intelligence-production experience, and Mind integration.
2. **Rustenwer owns** model architecture and engineering, adaptation and fine-tuning, training strategies and pipelines, model-engineering dataset preparation, optimization and compression, evaluation methodologies, quality assessment, checkpoint evaluation and selection, model packaging and inference preparation, and model-specific reproducibility/provenance.
3. **Syrius owns** RL environments, simulation interfaces, Gymnasium-compatible environments, rollout generation, reward and termination semantics, RL algorithms and policy implementations, policy training, RL experiment design, policy evaluation and comparison, checkpoint selection and promotion criteria, RL-specific reproducibility and metrics.
4. **Modal is the only initial remote compute provider.** No RunPod, AWS, Kubernetes, or other remote provider is introduced at any stage. Local development, lightweight processing, and tests stay local.
5. **Integration contract (conceptual, §6 of the directive):** Polygrow requests a specialized intelligence operation → the domain project validates the domain operation, defines the execution logic, and produces a workload specification → Polygrow's compute interface validates, authorizes, budgets, selects a runtime profile, and executes via the Modal adapter → a normalized job result returns → the domain project interprets it. The interface supports: submit a workload, inspect status, retrieve logs/progress, request cancellation, retrieve output artifact references, inspect execution metadata.
6. **Stable domain contracts** are defined around domain intent, not Modal details. Rustenwer verbs: `model_training`, `model_finetuning`, `model_evaluation`, `model_optimization`, `model_inference`. Syrius verbs: `environment_simulation`, `rollout_generation`, `policy_training`, `policy_evaluation`, `rl_experiment`. A workload specification describes domain operation, input artifact references, immutable configuration, required runtime profile, timeout/resource constraints, output expectations, and reproducibility metadata — never raw Modal SDK parameters.
7. **Transitional adapter rule:** if Polygrow's compute interface is not ready, a domain repo may carry a small, clearly isolated, explicitly transitional Modal adapter using the same workload contract where practical. It must be small, replaceable by Polygrow's managed interface without rewriting domain logic, and must not introduce a second provider.
8. **Lowest-friction first integration:** expose each domain system as an MCP server (tools = the §4 verbs) consumed by Polygrow's existing outbound MCP client. This needs no new plumbing in Polygrow, no shared library, and no synchronized releases. The HTTP APIs remain the fallback path.
9. **Provider execution success ≠ domain-quality success.** A completed Modal job is not a successful model or a learned policy. Rustenwer's promotion gate and Syrius's independent evaluation stay the arbiters of quality.

## 8. Backward-compatibility risks

### 8.1 Rustenwer

1. **In-memory everything is the default persistence.** Every router holds a module-level `InMemory*Repository`; swapping to Supabase/Postgres (or a Polygrow-owned store) touches ~20 routers and all tests that rely on fresh-per-test repos. The Protocol seams exist, but no Postgres implementation exists and migrations 001–011 were never applied — schema drift risk is real.
2. **The `ComputeProvider` Protocol is SSH/subprocess-shaped.** Its contract (`start` with a shell `command` list + `workdir`, `poll` by exit code, `fetch_events` by scp/cat) assumes a machine you SSH into. A Modal provider (function-based, no persistent machine, no SSH, artifacts via Modal volumes) fits only loosely — `ExecutionHandle` (pid/droplet_id/ip) and the runner's local-filesystem assumptions (`strategy.json` in attempt dir, `events.jsonl`, `final.json`) need reshaping, and the DO provider's destroy-on-stop semantics don't map to Modal.
3. **Training adapters assume a local filesystem + torch importable in-process.** Adapters load checkpoints via `torch.load`, write artifacts to local paths, and the runner is spawned as `python -m app.training.runner` inside a clone of this repo (the DO cloud-init literally `git clone`s SRogDev/rustenwer). Modal execution needs the adapter code packaged as a Modal image/function, not a repo clone — the "clone the repo onto the GPU machine" pattern is baked in.
4. **Auth is a stub with a fixed dev identity.** Any non-`rw_` bearer token becomes OWNER of a fixed org. Exposing this API to Polygrow as-is would grant full access; the real auth (Supabase JWT) was never wired, and the `rw_` key system is a separate, parallel mechanism. A Polygrow service-to-service auth model must replace both paths, not just one.
5. **Domain types are hand-synced Python ↔ TypeScript** (`shared/domain.py` ↔ `shared/types.ts`) with no codegen. Any domain change for the Polygrow contract (e.g. a Modal job reference, a Polygrow tenant id, a new `IntelligenceStrategy`) must be edited twice by hand; drift is already a documented hazard, and the web client hardcodes `localhost:8000`.

### 8.2 Syrius

1. **No auth, no tenancy, no per-tenant isolation — the API is wide open.** Every route trusts the caller; `Project.workspace_id`/`owner_id` are nullable FKs with no enforcement, and `User`/`Workspace` have no routes. Bolting Polygrow auth/tenancy on later means retrofitting every router + the job queue (jobs carry no tenant id) — a breaking change to all 44 paths if done properly.
2. **Local-filesystem coupling is load-bearing, not incidental.** The executor always uses `LocalStorage()` with `local://` URIs; `resolve_local_path` is the only way evaluation/export load a model; `GET /experiments/{id}/history` reads `metrics.csv` from local disk. Moving training to Modal breaks evaluation, export, history, and download simultaneously unless a shared/remote storage backend (and URI scheme) replaces `local://` everywhere at once — and `S3Storage` exists but is unwired and untested in this path.
3. **Single-checkpoint, CPU-only, single-process assumptions are baked into the data model.** One `final_model.zip` per run, "latest by step" selection, `training_engine: "stable-baselines3 PPO (CPU)"` hardcoded in the manifest, worker capabilities hardcoded to 4 local job kinds, 300 s lease with in-process heartbeat. Remote/GPU execution changes checkpoint granularity, lease/heartbeat timing, and the manifest's engine/worker fields — old manifests and old `Policy` rows (pointing at `local://` artifacts) become unloadable.
4. **The generic tool-dispatch endpoint runs code synchronously in the request.** `POST /capabilities/tools/{name}/run` executes handlers inline (including export via `_FakeJob`), unlike the 202 job path. If Polygrow exposes this as the RL contract, a long training/eval call blocks the request and bypasses queue, lease, retry, and cancellation semantics — any future async-by-default contract breaks existing callers of this endpoint.
5. **Reproducibility metadata is incomplete and partly hardcoded.** `env_version` is hardcoded `1` in `execute_export`; no git/commit, dataset, or container-image hash in the manifest; baseline reward is documented non-reproducible with the same seed. A Polygrow-side "reproduce this run" guarantee built on today's manifest would silently fail for env-version and code-version drift; changing the manifest schema breaks `VerifyReproducibility`/`InspectPolicyManifest` consumers and already-exported packages in `var/results/`.

### 8.3 Cross-system

- **Polygrow's Spec B must work independently of both domain repos** (§2.3 of Spec B). Integration is optional. Any design that makes the Intelligence platform _require_ Rustenwer or Syrius violates the spec.
- **Two registries, two `Intelligence` notions:** Polygrow's Spec B `Intelligence` (9 states) and Rustenwer's `Intelligence` (product entity with versions + promotion) must be aligned by identifier and provenance, never merged by force. Syrius has no `Intelligence` entity at all — its shippable unit is the `Policy` package.
- **Rollback:** every significant migration keeps the previous execution path available during validation; new workloads can be disabled independently; failed migrations must not corrupt existing model/experiment records; existing artifacts remain accessible.
