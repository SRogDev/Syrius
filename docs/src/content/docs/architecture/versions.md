### TanStack Start SPA config (verified, not assumed)

Verified two ways: the official `@tanstack/cli` scaffold (which produced a
working build for `@tanstack/react-start` 1.169.5) and the Start docs as
mirrored in current guides.

- Plugin import: `tanstackStart` from `@tanstack/react-start/plugin/vite`.
- SPA mode: `tanstackStart({ spa: { enabled: true, prerender: { outputPath: '/index.html', crawlLinks: false } } })`.
- Plugin order: `tailwindcss()`, `tanstackStart(...)`, `viteReact()`.
- File layout: `src/router.tsx` exporting `getRouter()`,
  `src/routes/__root.tsx` with `shellComponent: RootDocument` (full HTML
  document), `src/routeTree.gen.ts` generated by `vite build` (committed,
  per the scaffold's gitignore).
- Compatibility: `@tanstack/react-start` 1.169.5 declares `vite: >=8.0.0`
  and `react: >=18 || >=19` peers — Vite 8.3.8 and React 19.3.1 satisfy
  both.

### TypeScript 6 vs 7

TypeScript 7.0.2 is the latest release, but the official `@tanstack/cli`
scaffold pins TypeScript `^6.0.2` (installed: 6.0.3). Phase 0 stays on
6.0.3: TS 7 is an untested major rewrite (native port) for this stack,
and adopting it is a deliberate future decision, not a silent bump.

### Deferred web libraries

`@tanstack/react-table` and `@tanstack/react-virtual` are in the plan but
**not installed** in Phase 0: no list/virtualized view exists yet, and
installing unused dependencies violates the minimal-scope rule. They land
with the first real table view (Phase 1+).

### Build backend note

The workspace uses `uv_build` (bundled with uv) as the build backend,
not hatchling: `uv sync` with hatchling failed in this sandbox because
the isolated build environment could not fetch `hatchling.build_meta`
from the index through the egress proxy, while plain package resolution
worked. `uv_build` needs no download. If a future environment needs
hatchling, that is a one-line change per `pyproject.toml`.

| Package           | Pinned     | Status                                            |
| ----------------- | ---------- | ------------------------------------------------- |
| gymnasium         | 1.4.0      | Installed; CartPole-v1 validated via `check_env`  |
| stable-baselines3 | 2.9.2      | Installed; PPO trained 20,000 steps on CPU        |
| torch             | 2.15.0+cpu | CPU build from the PyTorch CPU index (see note)   |
| langgraph         | 0.6.8      | Installed; StateGraph + MemorySaver for workflows |

Torch CPU note: the `[tool.uv.sources] torch = { index =
"pytorch-cpu" }` entry only takes effect when torch is a **direct**
dependency — as a transitive SB3 dependency uv kept resolving the
CUDA build from PyPI (verified with an isolated test project). The
fix is the explicit `"torch==2.15.0"` pin in
`apps/api/pyproject.toml`. LangGraph 0.6.9 is yanked on PyPI, hence
the 0.6.8 pin.

## Docker

PostgreSQL image: `postgres:16-alpine` (healthcheck via `pg_isready`,
named volume `syrius_pgdata`). The Docker daemon was **not running** in
the build sandbox (`docker info` fails: no `/var/run/docker.sock`), so
`docker compose up` and the `docker build` of the API/worker images are
**Blocked / unverified** — recorded in `IMPLEMENTATION_STATUS.md`. The
Compose file and Dockerfiles are standard and syntactically checked with
`docker compose config` where possible without a daemon.
